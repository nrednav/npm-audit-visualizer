# npm-audit-visualizer

A web-based tool to visualize audit reports generated by `npm audit`.

> Disclaimer: This tool is still in its alpha phase.

## Interface

The report opens as a triage workspace: an editorial briefing with the total
finding count, a severity ledger that filters the explorer, the dependency
scope, and a vulnerability explorer with table and graph views. Table rows open
in place to show advisory detail, vulnerable ranges, and dependency paths.
The header includes a light and dark theme switch. The initial theme follows
your operating-system preference, and an explicit choice is stored locally.

Run the tool locally for the live interface. The screenshots in `assets/` show
the previous UI and are kept for project history.

## Get the tool

```shell
npm install -g npm-audit-visualizer
```

To verify that the installation was successful, please try the `--help` flag:

```shell
npm-audit-visualizer --help
```

The command installs with no dependency tree of its own. Everything it needs is
bundled into one file, so `npm install` adds exactly one package and nothing
else reaches your global `node_modules`.

### Verify a download

The npm registry records a SHA-512 integrity hash for every published version
and checks it again on install, so a corrupted or tampered download fails
installation rather than running. To check a version you already have, or one
you downloaded as a tarball:

```shell
# The hash the registry recorded for this version
npm view npm-audit-visualizer dist.integrity

# The hash of a tarball you downloaded
openssl dgst -sha512 -binary npm-audit-visualizer-*.tgz | openssl base64 -A
```

Prefix the second command's output with `sha512-` and compare it to the first.
A match means the bytes you hold are the bytes that were published.

## Usage

Navigate to any Node project and run the command with no arguments. It runs
`npm audit --json` in that directory and serves the result:

```shell
cd your-project
npm-audit-visualizer
```

The audit runs against the directory you invoked the command from. Your npm
configuration and registry apply, and no report file is created.

If you already have a report, pass it instead. The command reads that file and
does not run an audit:

```shell
npm audit --json > audit.json
npm-audit-visualizer -f audit.json
```

By default, this opens a new page in your web browser at
`http://localhost:1248`, or the next free port if that one is taken. The address
is printed before the browser is asked to open, so a machine without a desktop
can still be reached manually. If port `1248` is busy, pass another one:

```shell
npm-audit-visualizer --port 3000
```

To serve without opening a browser:

```shell
npm-audit-visualizer --no-open
```

For a guided walk through reading and acting on a report, see
[How to read an npm audit report](docs/how-to-read-a-report.md). For option
defaults, exit codes, routes, and the payload schema, see the
[CLI and payload reference](docs/cli-reference.md).

## About

### What

`npm-audit-visualizer` is a web-based tool to visualize audit reports generated
by `npm audit`.

### Why

With v7 of npm, the `npm audit` command was updated & it no longer displays
results in a tabular format.

While the new format is still useful, there were some visual elements to the old
tabular format that made it easier to trace vulnerability paths & dependencies.

As a result, the goal of this tool is to re-provide a visual interface for audit
reports, which can hopefully make it quicker and easier to identify and resolve
vulnerabilities within npm-managed projects.

## Development

This section will describe how to get the project setup for local development.

### Dependencies

To work with this project, you will need to have the following dependencies
installed:

- Node.js 26.13.1, the pinned Active LTS line in `.nvmrc` and `.node-version`
  - [Official](https://nodejs.org/en/download)
  - [fnm](https://github.com/Schniz/fnm)
  - [nvm](https://github.com/nvm-sh/nvm)
- npm 11.20.0, the version Node.js 26.13.1 ships and `packageManager`
  declares

### Get the source

This project is hosted at: https://github.com/nrednav/npm-audit-visualizer

HTTPS:

```shell
git clone https://github.com/nrednav/npm-audit-visualizer.git
```

SSH:

```shell
git clone git@github.com:nrednav/npm-audit-visualizer.git
```

### Install

To install the project's dependencies:

```shell
cd npm-audit-visualizer/
npm install
```

`.npmrc` sets `engine-strict=true` and `save-exact=true`. An install on a
different Node version stops with `EBADENGINE` instead of producing a tree that
was never verified, and a new dependency is written at one exact version.

There are no install-time Git hooks. Run `npm run check` before committing.

### Layout

The repository is one npm workspace with three packages. Each one answers a
different question, and the dependency arrows only point one way.

| Package             | Question                                             | Runtime |
| ------------------- | ---------------------------------------------------- | ------- |
| `packages/contract` | what shape is a report, and what shape is a payload? | either  |
| `packages/host`     | how does one report become one page?                 | Node    |
| `packages/surface`  | what does the page draw?                             | browser |

`contract` imports nothing but zod, so both runtimes can load it. `host` never
imports the surface's source, and `surface` never imports the host. Their only
agreement is the contract, which is checked before either one draws anything.

`test/boundaries.test.ts` enforces those edges.

### Build

```shell
npm run build
```

Builds the contract, then the surface, then the host, in that order. The host's
build copies the surface output into `dist/surface`, so one `npm publish` ships
one working command.

### Check

```shell
npm run check
```

Runs the formatter and linter, then the type checker for every package, then the
tests, then the build. This is the gate to pass before opening a pull request.

Individual steps:

```shell
npm run lint
npm run format
npm run typecheck
npm run test
```

The suite runs in two projects: `node` for the contract and the host, `jsdom`
for the surface. Tests resolve the contract to its source, so no build is needed
to run them.

### Run from source

```shell
npm run dev -- -f <path/to/audit.json>
```

`dev` builds and then starts the packaged command, because the interface is
served from the built directory. For iteration on the interface alone:

```shell
npm run dev:surface
```

That starts Vite on the surface with a hot reload; it needs a report served at
`/report.json`, which `npm start` provides.

Add `-d` to print the stages the run goes through:

```shell
npm run dev -- -d -f <path/to/audit.json>
```

### Keeping the foundation current

The runtime pin is checked against the official Node.js release schedule, not
against a date written here:

```shell
npm run check:support
```

It exits 0 when the pinned line is LTS or maintenance, 1 when the line has
ended or is not yet LTS, and 2 when the schedule could not be read. A line that
is `Current` does not pass, because a foundation meant to carry feature work
should not rest on a line that can still take breaking changes.

Three automated rhythms keep the tree from drifting back:

| Where            | When                             | What it does                                                                                                          |
| ---------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `verify.yml`     | every push and pull request      | clean install, package-manager check, full `npm run check` on Ubuntu                                                  |
| `drift.yml`      | Mondays at 06:00 UTC, or by hand | reruns verification, `npm audit`, `npm outdated`, and the support check                                               |
| `dependabot.yml` | Mondays at 06:00 UTC             | proposes npm and GitHub Actions updates, grouped for minor and patch, separate for majors, never merged automatically |

A red scheduled run is the signal to act. Minor and patch proposals usually
land as one grouped change; a major proposal is a migration and gets the full
suite to itself.
